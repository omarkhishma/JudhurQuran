## 1. Read this first

### What this bundle is
Everything in `prototypes/` is a **design reference built in HTML**. These files are working, clickable prototypes that show the intended look, layout, copy, interaction model, and state transitions of the product. They are **not production code and should not be shipped or copied verbatim**.

Your task is to **recreate these designs in a real application environment**, using that environment's established patterns, component library, routing, and data layer. No frontend or backend stack has been chosen — see `11-implementation-plan.md` §1 for the recommendation and the constraints that should drive the choice.

The prototypes fake their entire backend: all data comes from one module (`prototypes/lexicon-data.js`) and all persistence is `localStorage` under `jadhr-*` keys. Replacing that fake with a real schema, API, and search cluster **is the project**. `07-data-model.md`, `08-api-contract.md`, and `09-search-architecture.md` specify that replacement.

### Fidelity: high
These are **hi-fi mockups**. Colors, typography, spacing, radii, shadows, motion, copy, and empty/error states are final and deliberate. Recreate the UI to match. Exact values are in `02-design-tokens.md`; per-screen measurements are in the screen documents. Where a prototype and this documentation disagree, **this documentation wins** — it records intent, the prototype records one implementation of it.

### The one hard product constraint
This is a **bilingual, bidirectional, typographically demanding** product. Arabic is not a localisation afterthought here — it is the primary content, set in a serif (Amiri) at large sizes, with optional vowel marks (*tashkīl*) that can be toggled, mixed inline with Latin transliteration and English glosses. Every layout decision in these designs is downstream of that. Treat RTL/LTR mixing, diacritic handling, and Arabic text shaping as first-class engineering concerns from commit one, not a phase-two polish task.

## 2. What the product is

**Jadhr** (جَذْر, "root") is a reading and research environment for classical Arabic. It is built on a single idea: Arabic vocabulary is generated by pouring three-consonant **roots** into **patterns** (*awzān*), so the right unit of study is not the word but the family. Every surface in the product is a different view of that same root graph.

Four audiences, in order of how the product introduces itself:

1. **Casual explorers** — arrive at a plain question box ("Ask"), get one clear card per word: meaning, audio, cousins, one attestation. No jargon unless they ask for it.
2. **Students** — read texts with a live dictionary, collect words, review them on a scheduler, work through curated collections and a classroom.
3. **Scholars** — nine historical dictionaries side by side, apparatus view, concordance with KWIC and distribution, morphological analyser, citation export, bulk data download.
4. **Editors/contributors** — build root-family graphs on a canvas, propose sense edits, review each other's proposals, publish graphs as citable read-only pages.

## 4. How to run the prototypes

Serve the `prototypes/` folder over HTTP (`npx serve prototypes` or any static server — `file://` will fail, the files use ES module imports) and open `Jadhr.dc.html`. That is the hub; every other screen is reachable from it.

The prototypes share state through `localStorage`, so behaviour is cumulative: look up words in the Reader, then open Notebook, Review Queue, Concordance, or Profile and you will see the consequences. To reset, use Profile → "Delete local data".

Start with this walk, which exercises most of the product:

1. `Jadhr.dc.html` → **Explore** → a collection → **Open** a word
2. That opens the Reader in **Ask** mode → **Go deeper** → the layered panel
3. Click any Arabic word in the passage → panel follows → open **Where next?**
4. **Map** in the trail breadcrumb → **Open in the editor**
5. In the editor: edit a card, **Publish**
6. Back to the Reader → **Suggest an edit** on a sense → `Review Queue.dc.html` → approve twice → back to the Reader to see the merged sense with its credit line
7. `Data & API.dc.html` → the changelog now shows that merge

## 5. Non-negotiables

These are the things most likely to be quietly dropped during implementation, and each one is load-bearing:

- **Tashkīl is a toggle, not a constant.** Diacritics must be stored and rendered separately from the consonantal skeleton. Search must be diacritic-insensitive; display must be diacritic-faithful. This affects the schema, the search analyser, and every text component.
- **One theme key across the whole product.** Reader and Editor must agree; the prototypes share `jadhr-theme`. Default light.
- **Never splice English into Arabic text runs.** Glosses sit in their own LTR italic element, outside the RTL run. Mixing them inside breaks bidi reordering and was explicitly fixed during design.
- **Minimum 44px touch targets** on every control below 900px width. The phone pass audited this at 390px.
- **Text contrast ≥ 4.5:1** against its actual background, including the accent-tinted word states and the dark theme.
- **Local-first behaviour.** The product works with no account; signing in is an upgrade, not a gate. Anonymous work must survive and migrate on sign-in.
- **Dark theme parity.** Every screen, overlay, and embed has a dark variant already specified. It is not optional.
